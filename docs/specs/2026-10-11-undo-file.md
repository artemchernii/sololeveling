# Take a file back

Journey: you drop a file, the number on the card is wrong, and the only
way out was a database fix. (11 Oct: "we need to make these reading more
reliable. I cant run fixes and db fixes after every update to clean the
mess.") You open the file where you already open it — account → the file
— press "take this file back", and the account is as it was before that
file. Right after a save, the card it lands on has "undo". You said "go,
logos after" to the mockup.

Mockup: `design/treasury-mockup/undo-file.html`.

## What changes

- **The opened file** (`AccountFileView` → `TakeBack` in
  `AccountFileBack.tsx`): one box under the file. It says what goes — "3
  rows and the balance of 11 Oct go." — and, where the file touched cash,
  a strip: the account now, and after. Then one button.
- **The press**: "taking it back…" at once; the sheet returns to the
  account with a tick, "Taken back. ActivoBank is €153.21 again." A
  refusal stays in the box: "Not taken back — nothing changed."
- **What goes** (`convex/undoFile.ts`, `takeBack`): the file's rows in any
  account (`logs.by_owner_intake`), its buys and sells, the positions it
  showed, the balance it set. Another file's row that was paired with one
  of these stays, unpaired. Typed rows and typed balances are never
  touched.
- **The balance** now carries its file (`stateSnapshots.intakeId`,
  written by `accounts.writeBalance`). One saved before today is found the
  way the account sheet already finds it: same amount, within three days,
  not typed, and only for the file that was read (not a second drop).
- **The file stays read** (`intakes.takenBackAt`): it leaves the account
  sheet; dropped again, its first reading is reused.
- **Right after a save** (`Applied` → `UndoSave`, `Undone` in
  `LandedUndo.tsx`, `undoFile.takeBackBatch`): "undo" beside "done" takes
  back every file of that drop, by the file's own mark only.

## Scenarios

e2e/undo-file.spec.ts, mock `e2eUpdate.readActivo` — your ActivoBank on 11
Oct: €153.21 read on 3 Oct, then IMG_9282 saved, €90.35.

- S1 open the file → the box, now €90.35, after €153.21 → press → taking
  it back… → "Taken back", €153.21, the file and its rows gone, Revolut's
  top-up row still there. Phone width: the box at 390px.
- S2 save → undo on the landed card → taking it back… → "Taken back" →
  done → the account is €153.21 with no file.
- convex-test (`undoFile.test.ts`): the same day's numbers; a balance
  carries its file; refusals (another user, not saved yet, taken back
  twice, a save with nothing left); a file that wrote a row in another
  account, and another file's row left unpaired; an older file under a
  newer balance.
- `src/lib/undoFile.test.ts`: the sentence — one or many, "15 positions
  and the cash", never a plus.

## Data

The strip is state plus logged rows after it, one currency: the pocket's
latest balance and what moved since (`aggregate.movedSince`, as the card
counts it), then the same with this file's balance and rows left out.

## Not in this slice

- The strip is cash only. A broker screen or a stocks file shows no
  account worth before and after (the mockup did); that needs prices.
- A broker screen saved before today keeps its cash balance when taken
  back — it was not marked with its file.
- What a file replaced when it was saved (an earlier balance or look of
  the same day) does not come back.
- No "put it back": drop the file again. Not tested end to end.
- Removing a typed balance; payee logos on rows (next, its own PR).
- The write failing in the browser is not in e2e (the refusals are in
  convex-test).
